# Firefly 事故响应

## 分级

- P0：认证越权、跨用户数据可见、数据丢失、生产完全不可用、生成成功但成片不可恢复。
- P1：主要生成/上传/预览链路持续失败，队列或备份长期异常。
- P2：局部交互、单一浏览器或可绕过的运维问题。

## 首十分钟

1. 记录 Case ID、UTC 时间、revision、image digest；禁止在群里粘贴密钥、Prompt 或签名 URL。
2. 查看 `/api/health/live` 与 `/api/health/ready`，再运行只读 `queue-status`、`backup-status` 和容器重启检查。
3. 若刚发布，优先触发蓝绿回滚；不要在生产容器内手改源码。
4. 保存相关结构化日志和 GitHub Actions 运行链接，确认影响用户和数据范围。

## 常见处置

- **队列堆积**：区分 wait/active/delayed/failed；确认 Redis 无 eviction、Worker 锁会恢复，再决定是否扩并发。禁止直接清空队列。
- **TOS 归档失败**：确认任务仍有未过期临时源；使用 `task-rearchive`。已有 output 时禁止覆盖。
- **海报/预览缺失**：output ready 后使用 `media-recover --kind poster|preview`。
- **疑似孤儿对象**：先运行 `tos-orphans`，只输出计数与样本；本工具不自动删除对象。
- **备份过期**：先恢复备份任务，不执行数据库迁移或发布。
- **跨用户访问**：立即禁用相关账号并撤销会话，保全日志，停止所有写发布，按 P0 处理。

## 结束条件

服务恢复不等于事故结束。必须确认指标稳定、补齐测试、记录根因/时间线/影响/恢复动作，并给出防复发 PR 和负责人。任何临时扩大权限、关闭门禁或手动数据修补都要撤销并审计。
